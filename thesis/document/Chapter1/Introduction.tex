Static application security testing (SAST) applies static program analysis to the security of software projects. MORE INFO ABOUT STATIC ANALYSIS HERE. Static analysis is performed on the source code, compiled byte-code, or some other representation of the source code \cite{NielsonFlemming2005Popa}. Popular SAST tools include: SonarQube \cite{sonarqube}, SpotBugs \cite{spotbugs}, Snyk Code \cite{snykcode}, and Facebook's Infer \cite{infer}. SAST tools have become widely used at all stages of the software development life-cycle. Furthermore, they have been demonstrated to be highly effective in identifying defects in code compared to other methods, such as manual inspection \cite{Nichols2020}.\\

\noindent
Unfortunately, SAST tools are not perfect. From Rice's Theorem, it is known that any non-trivial property about programs is reducible to the halting problem. That is, it is undecidable --- a "perfect" analysis is not always possible \cite{moller2012static}. As such, SAST tools are required to make approximations, resulting in an imperfect output --- i.e. false positives (where safe code is incorrectly labelled as a defect) and false negatives (where the analysis misses a genuine fault) \cite{chess2004static}. False positives are not ideal as manual inspection is required to separate genuine defects from false positives, leading to an increased time and labour cost. And, to reduce the rate of false negatives, manual configuration of the SAST tools for specific software projects is often required \cite{ZampettiFiorella2017HOSP}.\\

\noindent
For example, to perform an effective taint analysis, a custom configuration of sources, sinks and sanitisers for a particular project is often required when the default configuration proves insufficient. Creating this manual configuration is a time-consuming and resource-intensive process. As such, methodologies to automatically label methods as sources, sinks, and sanitisers may enable existing taint analysis tools to operate more effectively. It should also be noted that in cases where a closed-source library is being used in a software project, it may be impossible to determine how the API methods should be labelled for the taint analysis.\\

\section{Topic Definition}

\noindent
Static application security testing (SAST) tools often require additional configuration to conduct a practical security analysis. Typically, this configuration is done manually and demands a substantial time, labour, and skill cost to be done effectively. While being an informal natural-language description of a Java method, Javadoc may contain valuable information for the configuration of SAST tools. With powerful pre-trained natural language processing models being made publicly available, it may be possible to train a deep learning model to extract relevant security properties from Javadocs and use this information to configure existing SAST tools.\\

\noindent
One such pre-trained model of particular relevance is Microsoft's CodeBERT. CodeBERT has been trained on natural language and numerous programming languages (including Java). CodeBERT understands the semantic connection between natural language and programming languages, making it suitable for downstream tasks involving the intersection of them \cite{CodeBERT}.\\

\noindent
It is hypothesised that CodeBERT can be fine-tuned with additional data to extract relevant security properties from Javadoc. This information can be used to configure existing static analysis tools. For example, taint analysis requires a list of methods labelled as sources, sinks, and sanitisers. Taint analysis tools often have a default configuration with popular and frequently used APIs. However, security-critical methods are not included in the default configuration, particularly in large projects. This leads to an incomplete analysis being conducted. Manual inspection is required to label additional methods and add them to the taint analysis configuration. Naturally, this is a labour-intensive process with high-skill requirements. Furthermore, in cases where a closed-source library is being used --- where only the binary and documentation are available --- it may be difficult or impossible to label these methods correctly. With sufficient training, it is believed codeBERT would be able to perform this task of labelling methods for taint analysis quickly and effectively.
