\noindent
Static application security testing (SAST) applies static program analysis to enhance a software project's security. Static analysis is performed on the source code, compiled byte code, or other representations of the source code \cite{principles_program_analysis}. Popular SAST tools include SonarQube, SpotBugs, Snyk Code, and Facebook's Infer. SAST tools are widely used at all stages of the software development life-cycle and have been demonstrated to identify software defects more effectively than other methods, such as manual inspection \cite{costs_static_analysis}.\\

\noindent
Unfortunately, SAST tools are not perfect. From Rice's Theorem, we know that any non-trivial property about programs is undecidable \cite{moller2012static}. A perfect analysis is not always possible, and approximations must be made for an analysis to terminate. False positives (where benign code is labelled as a defect) and false negatives (where a genuine fault is missed) \cite{chess2004static} are common in all static analysis tools. False positives are not ideal as manual inspection is required to isolate genuine defects, leading to an increased time and labour cost. Despite this fundamental limitation of static analysis tools, there are numerous methodologies for increasing the performance of SAST tools. Namely, manual configuration. \\

\noindent
Manual configuration of SAST tools is often required to reduce the rate of false negatives, and false positives \cite{ZampettiFiorella2017HOSP}. A custom configuration of sources, sinks, and sanitisers is often required to perform an effective taint analysis. Generally, taint analysis tools include a default configuration with a list of security-sensitive methods from popular APIs. For example, all good taint analysis tools would include the \emph{getParameter()}\footnote{\href{https://docs.oracle.com/javaee/6/api/javax/servlet/ServletRequest.html\#getParameter(java.lang.String)}{Link to the method's Javadoc}} method from the ServletRequest interface as a \emph{source} by default.\\

\noindent
If a software project uses a niche library or proprietary code, any taint analysis tool will likely not have the security-sensitive methods from those libraries in its configuration. Therefore the taint analysis tool will produce an incomplete analysis. One can manually identify relevant security-sensitive methods and add them to the configuration to improve the taint analysis. However, this is time-consuming and error-prone. The ability to automatically classify a software project's security-sensitive methods may reduce the time required to configure taint analysis tools and produce a comparatively more complete and precise configuration. Ultimately, this would enable taint analysis tools to perform more effectively. \\

\noindent
Numerous approaches exist to perform this automatic classification task, such as pattern-matching or dynamic analysis techniques. For example, \emph{Merlin} \cite{merlin} uses interprocedural analysis combined with probabilistic inference to classify security-sensitive methods automatically. However, in light of recent developments in machine learning, deep learning (more specifically, models based on the Transformer architecture) may prove effective for this task. Recently, Microsoft has made publicly available two pre-trained models, CodeBERT and UniXcoder, that excel in tasks involving the intersection between natural language and code. These pre-trained models could prove useful for this task. \\

\noindent
Using machine learning to classify security-sensitive methods is not novel. For example, \emph{SuSi} \cite{susi} uses a Support Vector Machine (SVM) on hundreds of hand-crafted features to identify sources, sinks, and sanitisers in the Android Framework. \emph{SWAN} \cite{swanassist} and Sas et al. \cite{autodetection} take similar approaches on arbitrary Java programs. These existing implementations extract their features from byte code only. To our knowledge, Javadoc has not been used for this task before. \\

\begin{itemize}
    \item Construct a training, validation, and test dataset of labelled security-sensitive Java methods.
    \item Produce a variety of machine learning models and configurations using CodeBERT and UniXcoder for the task of classifying security-sensitive Java methods.
    \item Fine-tune and train these models on our custom dataset.
    \item Evaluate the performance of these machine learning models in the context of a realistic use case (our test dataset).
\end{itemize}
