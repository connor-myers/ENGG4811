\noindent
Static application security testing (SAST) applies static program analysis to the security of software projects. Static analysis is performed on the source code, compiled byte-code, or some other representation of the source code \cite{principles_program_analysis}. Popular SAST tools include: SonarQube, SpotBugs, Snyk Code, and Facebook's Infer. SAST tools have become widely used at all stages of the software development life-cycle. Furthermore, they have been demonstrated to be highly effective in identifying defects in code compared to other methods, such as manual inspection \cite{costs_static_analysis}.\\

\noindent
Unfortunately, SAST tools are not perfect. From Rice's Theorem, it is known that any non-trivial property about programs is reducible to the halting problem, i.e., undecidable \cite{moller2012static}. That is, a perfect analysis is not always possible, and approximations must be made in order for the analysis to terminate, resulting in an imperfect output. False positives (where safe code is incorrectly labelled as a defect) and false negatives (where the analysis misses a genuine fault) \cite{chess2004static} are common in all static analysis tools. False positives are not ideal as manual inspection is required to isolate genuine defects, leading to an increased time and labour cost whereas false negatives mean that genuine software faults are left undetected by the analysis. Despite this fundamental limitation of static analysis tools, there are numerous methodologies for increasing the performance of these SAST tools. Namely, manual configuration. \\

\noindent
To reduce the rate of false negatives, manual configuration of the SAST tools for specific software projects is often required \cite{ZampettiFiorella2017HOSP}. For example, to perform an effective taint analysis, a custom configuration of sources, sinks and sanitisers for a particular project is often required. Taint analysis tools are not yet sophisticated enough to implicitly categorise methods as sources, sinks, and sanitisers; taint analysis tools require sensitive methods to be pre-labelled to conduct the analysis. Generally, these tools come with a default configuration containing a list of sensitive methods in popular APIs. For example, the \emph{getParameter()} method as a part of the ServletRequest interface would likely be listed by all taint analysis tools as a \emph{source} since it is retrieving untrusted input from the user. Of course, if a project is using a niche library or code developed in-house, the taint analysis will not be able to incorporate those data-points into its analysis, leading to sub-optimal output. To improve the taint analysis, one can manually identify the sensitive methods in a software project and add these to the taint analysis' configuration. Creating this manual configuration is often a time-consuming and resource-intensive process. As such, methodologies to automatically label security sensitive methods may enable existing taint analysis tools to be configured automatically and therefore operate more effectively without the burden of manual configuration.\\

\noindent
There are numerous approaches one may take to perform this automatic classification of security sensitive methods, such as pattern-matching or dynamic analysis. For example, \emph{Merlin} \cite{merlin} uses interprocedural analysis combined with probabilistic inference to automatically classify security sensitive methods.  In light of recent developments in machine learning, deep-learning may prove an effective technique for security-sensitive method classification.\\

\noindent
Using machine learning (excluding deep-learning) to classify security sensitive methods is not novel in the literature. For example, \emph{SuSi} \cite{susi} uses a Support Vector Machine (SVM) on hundreds of hand-crafted features approach to identify sources, sinks, and sanitisers in the Android Framework. \emph{SWAN} \cite{swanassist} takes a similar approach on an alternative dataset. Likewise, Sas et al. \cite{autodetection} also uses an SVM on a number of hand-selected features. Notably, none of these aforementioned papers make use of natural-language descriptions of code, nor the source-code itself. They operate entirely out of features extracted from Java \emph{byte}-code. \\
