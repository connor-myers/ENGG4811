\section{Similar Tasks}
There are numerous similar tasks in the literature. That is, applying machine-learning to the classification of security-sensitive methods. Here we will detail the more relevant papers in the literature.

\subsection{SuSi}

\noindent
SuSi \cite{susi} is a machine-learning approach for identifying sources and sinks in \emph{Android} code. SuSi uses a support vector machine (SVM) with a large number of features as its machine-learning model. SuSi employs a Support Vector Machine (SVM) approach on 144 manually defined binary features (i.e., does the method have this feature --- true or false?) to perform its classification. That is, the SuSi authors have manually identified what aspects of a method's code is important for classifying it as a security sensitive method. \\

\noindent
For example, one of the 144 features SuSi classifies on is whether or not the class name the method belongs to contains the keyword `get' (the reason for this being that methods that are `getting' a value are more likely to be a \emph{source}; e.g., HttpServletRequest.getParameter()). While this may seem like a simple feature, which it is, when combined with 144 additional features a high accuracy can be reached on a relatively small training dataset.\\

\noindent
Importantly, this methodology is decidedly different than our proposed approach of fine-tuning a pre-trained bimodal transformer model. Rather than manually identifying the features, it is hoped the powerful pre-trained bimodal model will be able to perform this process automatically. That is, automatically learn how to classify security-sensitive methods. SuSi also differs from our proposed approach as it only operates on the code; no features of the Javadoc are included in the SVM. Furthermore, SuSi only classifies methods as sources, sinks, or none. It does not classify sanitisers, whereas our proposed approach will.\\

\noindent
SuSi's labelled dataset is available and open-source. However, despite the code technically being Java (as most android code is written in Java), for our purposes we will restrict the training dataset to native Java examples. Android Java code tends to use android-only libraries and, in general, looks very different to `normal Java code'. As such, it is thought it would affect the performance of the model on traditional Java code if these Android examples were included. Hence, we will not be including SuSi's dataset in our final training dataset.\\

\noindent
SuSi performs extremely well, achieving a 91.9\% recall and a 91.9\% precision.

\subsection{Swan}

SWAN is an automated classifier of security-sensitive methods in Java using machine-learning \cite{swanassist}. SWAN works almost identically to SuSi (i.e., SVM on a number of manually identified binary features), except it is trained on general Java programs and is trained on more features (206 for SWAN versus 144 for SuSi). SWAN classifies code as a source, sink, sanitizer, authentication-method, or none --- which is identical to our task, with the inclusion of the \emph{authenitication-method} security-sensitive method type. SWAN is also able to further classify some of these methods according to their specific CWE (Common Weakness Enumeration), however this aspect of SWAN is not relevant to this thesis. \\

\noindent
SWAN's training dataset is publicly available and open-source \cite{swan_github}. Labelled datasets of security-sensitive methods are hard to come by, and thankfully Swan has quite an extensive list. For this thesis, we will be including a subset of this dataset (we remove \emph{authentication-method} examples, add \emph{none} examples which are not included in SWAN's public dataset, and remove unsuitable examples according to our own filtering rules) for our own training and evaluation purposes. Furthermore, SWAN does not provide its testing or validation dataset so we will split up their training set to get testing and validation examples.\\

\noindent
This dataset does not provide the code and Javadoc associated with each method, so additional processing of this data is required. We will come back to this later in the thesis. \\

\noindent
The \emph{SWAN} project also includes SWAN-assist, which is an Intellij plugin that allows users to classify security-relevant methods while working on a project. SWAN includes this additional information to improve the machine-learning classifier for a particular project. Of course, this aspect is not relevant to our project but it does inflate the accuracy of the model when compared to a fully-automated process such as ours. \\

\noindent
SWAN-base (i.e., SWAN without additional information from users using SWAN-assist) achieves an accuracy of $0.826$ on classification of security-sensitive methods \cite{swanassist}. While it would be good for our model to achieve an accuracy higher than this, it should be noted that it is not a fair comparison. For one, we will be operating on a subset of SWAN's base training-set out of necessity, and will be classifying on four labels, not five. Naturally, classifying on fewer labels is likely to inflate the accuracy of our model compared to SWAN-base, whereas operating on a subset on the dataset is likely to reduce the accuracy of our model relatively.

\subsection{Sas et al.}

\noindent
Sas et al. \cite{autodetection}, like SuSi and SWAN, uses an SVM on a variety of features to perform its classification. Sas et al. uses the least number of features (roughly 100) compared to SuSi and SWAN. Like SWAN, it was developed in hopes of identifying security-sensitive methods in general Java code, as opposed to SuSi which classified Java code for Android. The model was trained on over 1000 methods manually identified from popular Java libraries including: Apache Commons IO\footnote{\url{https://commons.apache.org/proper/commons-io/}} and Apache HTTP Client\footnote{\url{https://hc.apache.org/httpcomponents-client-5.1.x/}}. \\

\noindent
Furthermore, Sas et al. does not classify on the same labels as SuSi or SWAN. It classifies on the four following labels: source, sink, mixed (both source and sink), and none (neither a source or sink). Unlike our proposed approach, it does not identify sanitisers, but it does include methods with behaviour reflective of both sources and sinks, i.e., mixed.\\

\noindent
The SVM model achieved an average (of all classes) recall of 85\% and an average precision of 77.9\%.\\ 

\noindent
Unfortunately, the training dataset is not publicly available and hence we will not be able to include it in our training data for this thesis.

\subsection{Pooling Types}
As mentioned earlier in the background knowledge section of this thesis, the type of pooling used in a model based on the transformer architecture is an important decision to be made. Typically, models based on BERT use a special \emph{CLS} (classification) token at the start of the input and use the final embedding of that single token to represent the embedding of the entire sequence. \\

\noindent
While CLS-pooling is a common technique, there is evidence in the literature that suggests alternative pooling techniques, such as mean-pooling and max-pooling, may be more suitable for in certain applications. For instance, experiments conducted for \emph{DefSent} \cite{tsukagoshi2021defsent} --- an NLP model which aimed to produce sentence embeddings for definitions of words to be similar to the word itself --- found inconclusive results on which pooling strategy worked best.\\

\noindent
For instance, when running the experiment on RoBERTa-base (recalling that CodeBERT and UnixCoder use an architecture identical to RoBERTa), they found no significant difference in the performance of the three pooling types, i.e., CLS, mean, and max pooling. SentenceBERT, another fine-tuned model trained on the same task as DefBERT, saw better performance using mean-pooling \cite{reimers2019sentence}. Finally, a paper by Ma et al., also regarding sentence embeddings of natural-language, says that despite CLS-pooling typically being used for fine-tuning for classification tasks, they found that mean-pooling performed best in all the categories they tested for \cite{ma2019universal}. This contradicts the default implementation of the sequence classification task for Roberta in HuggingFace, which uses CLS-pooling.\\

\noindent
With all this evidence in mind, it suggests we should try these three popular pooling types for our model to determine which is the best-performing for our use-case, as the literature is suggesting there is no definitively best pooling strategy. \\

\noindent
As eluded to earlier, this poses an issue as HuggingFace's default implementation of SequenceClassification for Roberta uses CLS-pooling, which means we will need to reimplement this class ourselves. Thankfully, the downstream tasks done by the CodeBERT authors for clone detection and blank show an example of how to do mean and max pooling respectively.
