\section{Similar Tasks}
There are numerous similar tasks in the literature. That is, applying machine learning to the classification of security-sensitive methods. Here we will detail the more relevant papers in the literature.

\subsection{SuSi}

\noindent
SuSi \cite{susi} is a machine learning approach for identifying sources and sinks in \emph{Android} code. SuSi uses a Support Vector Machine (SVM) classifier with 144 manually defined binary features (i.e., does the method have this feature --- true or false?) to perform its classification. \\

\noindent
For example, one of the features used is whether or not the class name the method belongs to contains the keyword `get'. While this may seem like a simple feature, which it is, when combined with 143 additional features, high accuracy can be reached.\\

% (the reason for this being that methods that are `getting' a value are more likely to be a \emph{source}; e.g., HttpServletRequest.getParameter()). 

\noindent
Importantly, this methodology is decidedly different from our proposed approach. For instance, SuSi uses manually curated features, whereas, in our approach, these features would automatically be generated. SuSi also differs from our proposed approach as it only operates on the code; no features of the Javadoc are included in the SVM. Furthermore, SuSi only classifies methods as sources, sinks, or none. It does not classify sanitisers, whereas our proposed approach does.\\

\noindent
SuSi's labelled dataset is available and open-source. However, despite the code technically being Java, we will restrict our training dataset to \emph{native} Java examples. Android Java code uses Android-only libraries and generally looks very different from `normal' Java. As such, it was thought included Android examples in the training data would negatively affect the model's performance on traditional Java code. Additionally, the dataset is not in a suitable format (it does not include Javadoc) and, if used, would require additional configuration to be useful for our purposes. \\

\noindent
SuSi performs exceptionally well, achieving an F1-score of 91.9\%.

\subsection{Swan}

SWAN is a semi-automated classifier of security-sensitive Java methods using machine learning techniques \cite{swanassist}. SWAN works almost identically to SuSi (i.e., SVM on a number of manually identified binary features), except it is trained on general Java programs and is trained on more features (206 for SWAN versus 144 for SuSi). SWAN classifies code as source, sink, sanitiser, authentication-method, or none --- which is a superset of the labels we are using. SWAN can also further classify some of these methods according to their specific CWE (Common Weakness Enumeration). However, this aspect of SWAN is not relevant to this thesis. \\

% \noindent
% SWAN employs a Support Vector Machine (SVM) approach on 206 manually defined binary features (i.e., does the method have this feature --- true or false?) to perform its classification. That is, the authors have gone through a dataset of examples of security-sensitive-methods and manually identified what aspects of a code is important for classifying it as a security sensitive method. This is decidedly different from our proposed implementation of fine-tuning a pre-trained bimodal Transformer model. \\

%\noindent
%For example, one of the 206 features SWAN classifies on is whether or not the class name the method belongs to contains the keyword `SQL' (the reason for this being that methods interacting with an SQL database are more likely to be a \emph{sink}). While this may seem like a simple feature, which it is, when combined with 205 additional features a high accuracy can be reached on a relatively small training dataset.\\

% \noindent
% The \emph{SWAN} project also includes SWAN-assist, which is an Intellij plugin that allows users to classify security-relevant methods while working on a project. SWAN includes this additional information to improve the machine-learning classifier for a particular project. Of course, this aspect is not relevant to our project, but it does inflate the model's accuracy compared to a fully-automated process such as ours. \\

\noindent
SWAN's training dataset is publicly available and open-source \cite{swan_github}. Labelled datasets of security-sensitive methods are hard to come by, and thankfully Swan has quite an extensive list. For this thesis, we will include a subset of this dataset for our training and evaluation purposes.  \\

\noindent
This dataset does not provide the code and Javadoc associated with each method, so additional data processing is required. We will return to this topic in Chapter \ref{dataset-creation}. \\

\noindent
SWAN achieves an accuracy of $0.826$ on the classification of security-sensitive methods \cite{swanassist}.

\subsection{Sas et al.}

\noindent
Sas et al. \cite{autodetection}, like SuSi and SWAN, uses an SVM classifier on many manually curated features to perform its classification. Sas et al. uses fewer features (roughly 100) than SuSi and SWAN. Like SWAN, it is trained on general Java code. The model was trained on over 1000 methods manually identified from popular Java libraries, including Apache Commons IO\footnote{\url{https://commons.apache.org/proper/commons-io/}} and Apache HTTP Client\footnote{\url{https://hc.apache.org/httpcomponents-client-5.1.x/}}. \\

\noindent
Furthermore, Sas et al. does not classify on the same labels as SuSi or SWAN. It classifies on the four following labels: source, sink, mixed (both source and sink), and none (neither a source nor a sink). Unlike our approach, it does not include sanitisers. \\

\noindent
The SVM model achieved an average (of all classes) recall of 85\% and an average precision of 77.9\%.\\ 

\noindent
Unfortunately, the training dataset is not publicly available, so we cannot include it in our training data for this thesis.

\section{Model Architecture}
\label{model_architecture}
\subsection{CodeBERT}
CodeBERT \cite{CodeBERT} is a large pre-trained model by Microsoft for code and natural-language tasks. It uses an architecture identical to RoBERTa\footnote{More specifically, RoBERTa-base with 125M parameters. See: \url{https://aclanthology.org/2021.ccl-1.108/}}, and has been trained on millions of bimodal\footnote{It has also been trained on some unimodal examples, i.e., code or natural-language alone for the Replaced Token Detection pre-training objective.} examples of code (Go, Java, Javascript, PHP, Python, and Ruby) and natural-language (English). For example, a Java method and its corresponding Javadoc. This makes it suitable for downstream tasks involving the relationship between natural-language and code. \\

\noindent
Since CodeBERT is based on RoBERTa, it uses the transformer architecture, which was briefly outlined in section \ref{transformers}. CodeBERT takes a maximum input of 512 tokens (510-511 usable, depending on what pooling style is used) and generates an embedding (Tensor) of size 768 for each provided token. As mentioned in section \ref{embedding}, we require a \emph{sequence} embedding (i.e., the embedding for the entire sequence), not a token embedding (i.e., the embedding for each token) to perform our classification. Hence, these 512 token embeddings need to be \emph{pooled} into a sequence embedding. We can either: take the mean of all the token embeddings element-wise (mean-pooling), take the maximum value of each of the token embeddings to construct a new size $768$ embedding (max-pooling), or simply take the embedding of the first token (the [CLS] (classification) token) and treat it as a our sequence embedding. \\

\noindent
Because CodeBERT is trained on learning the relationship between code and natural-langauge, this makes it suitable for tasks involving the intersection of code and natural-language. CodeBERT was benchmarked by the creators on downstream tasks including: documentation generation (generates natural-language description of code from segment of code), and natural-langauge code-search (provides semantically most related code from natural-langauge description). While none of these tasks are a classification task, as our task is, CodeBERT can easily be augmented to be a classification model by adding an additional classification head on top of CodeBERT. \\

\noindent
In fact, since CodeBERT's architecture is \emph{identical} to RoBERTa-base (the structure of the neural network for the two models is exactly the same; they differ only in the weights and biases to be loaded) we can use existing classification code for RoBERTa-base (a much more popular and well-supported model, compared to CodeBERT) provided in the HuggingFace Transformer's library\footnote{More information on this library can be found here: \url{https://huggingface.co/docs/transformers/index}}, with only slight modifications, to implement our model.\\

\noindent
Of course, CodeBERT has not been trained on our exact task. The pre-trained model of CodeBERT has been trained two tasks that are far more general than any downstream task. Specifically, CodeBERT has been pre-trained on Masked Language Modelling (MLM), and Replaced Token Detection (RTD).\\

\noindent
In Masked Language Modelling, for each bimodal training example, 15\% of the tokens are masked (i.e., hidden) from CodeBERT and CodeBERT must `guess' what the hidden tokens were. From this guess, a loss value is generated depending on how good CodeBERT's guess was and the weights and biases are then optimised in the usual fashion (i.e., gradient descent). For Replaced Token Detection, CodeBERT is provided unimodal data (code \emph{or} natural-language) and a certain number of tokens are replaced with other tokens. Then, CodeBERT must classify each token as replaced or not replaced. Of course, a loss is generated depending on how accurate the classification was and the model is optimised accordingly. \\

\noindent
Because CodeBERT has only been trained on these two general tasks, for it to classify security-sensitive methods accurately, it will need to be fine-tuned, as described in Section \ref{fine-tuning}.

\subsection{UniXcoder}
\noindent
UniXcoder is another large pre-trained model created by Microsoft for code and natural-langauge understanding \cite{unixcoder}. UniXcoder is similar to codeBERT in that it was trained on both code and natural-language, and both have 12 layers with 768-dimensional hidden states (i.e., they are the same size)\footnote{This information is not conveyed in the CodeBERT paper directly, but CodeBERT is mentioned to be the same size as roberta-base \cite{CodeBERT}, and roberta-base is described as having 12 layers with 768-dimensional hidden states \cite{roberta}.}. However, these two models differ in key areas. Firstly, unlike codeBERT, UniXcoder is not trained on code directly, but rather on a special abstract syntax tree (AST) generated from the code\footnote{The pseudo-code for the algorithm used to generate the AST can be found at \cite[pg.~3]{unixcoder}}. Secondly, UniXcoder is an encoder-decoder model, unlike codeBERT which is solely an encoder-model \cite{CodeBERT}. Although, this distinction is less importantant for us as, for our task, we will be running UniXcoder in encoder-only mode.\\

\noindent
For the encoder-only mode, UniXcoder, like CodeBERT, was also trained on the Masked Language Modelling (MLM) objective. For our purposes, since we are not using the decoder mode of UniXcoder, the only fundamental difference between the two models is that UniXcoder was pre-trained using the AST of code instead of the code directly. In the CodeBERT paper, the authors hypothesised that their model was performing worse than another model, Code2Seq \cite{code2seq}, for certain tasks because Code2Seq leverages the syntactic structure of programs (i.e. a program's AST) during pre-training \cite{CodeBERT}. As such, the development of UniXcoder can be thought of as an extension to CodeBERT in which the syntactic structure of the program is incorporated into pre-training.

\subsection{SVM tf-idf}

\noindent
Term-frequency inverse-document frequency methods (as detailed in Section \ref{tf-idf}) are useful for feature extraction for SVMs. In fact, this is quite a common technique for classifying natural-language \cite{sentiment-analysis-cb} \cite{sentiment-analysis-fin}. That is, one uses tf-idf methods to extract a list of features important to each label for which they want to classify, and then they train an SVM on that list of features. \\

\noindent
Because an SVM using tf-idf features is, arguably, the most simplistic way of performing text classification, i.e., a linear model using basic statistical methods to extract features, it will be considered the `baseline model'. That is, the accuracy generated by an SVM-tf-idf model is the bare minimum our advanced fine-tuned transformer-architecture models will need to meet to be considered even remotely successful. \\

\noindent
SVM with tf-idf are typically implemented using the Python library `Scikit-learn' \cite{scikit-learn}, hence we will be using this library to implement this model.

% Tf-idf is particularly useful for SVMs as it extracts the terms that are important for a particular label, but are not as important in other labels. Then, the features that our SVM will be trained on are simply the binary result of whether or not the provided example contains any of these important keywords or not.\\

\subsection{SVM-Transformer Hybrid}

\noindent
A less common technique, but perhaps more interesting, is to combine both SVM and Transformers to implement a classification model. This is typically done by using a transformer model to generate a contextualised sequence embedding for input texts, and use those embeddings as the features to train an SVM model. This technique does have a precedent in the literature \cite{svm-with-transformer} \cite{svm-with-embeddings}. Since we are using both CodeBERT and Unixcoder, we will conduct experiments on training an SVM with both CodeBERT and UnixCoder embeddings. \\

\noindent
This raises an interesting idea. Since we are already fine-tuning CodeBERT and Unixcoder with labelled data, what would happen if we generated the features for our SVM using the \emph{fine}-tuned model of CodeBERT and Unixcoder respectively. So far, we have discussed using the pre-trained models --- trained on those two unsupervised tasks of MLM and RTD --- to generate these features, but not using the fine-tuned version of these models. \\

\noindent
Piskorski et al. carried out this experiment. That is, as part of their evaluation of a multitude of different models, they compared an SVM model being fed features from a fine-tuned BERT model and the base pre-trained BERT model. They found the SVM model using fine-tuned embeddings outperformed the SVM model using the base pre-trained embeddings to be, on average across the three experiments conducted, to be $8\%$ more accurate\footnote{As we will come to find, extracting extra-accuracy when approaching accuracies greater than $80\%$ is not insignificant.} \cite{svm-with-embeddings}. \\

\noindent
To clarify how this will work: when we fine-tune codeBERT (and UnixCoder, for that matter), we will add an additional classification-head to the standard pre-trained model to perform the classification. Then, we will fine-tune the model on the labelled data we provide it. However, since we are not freezing any of the lower-layers, the original base model (the pre-trained model) that we added the classification head to \emph{also} has its weights and biases adjusted during fine-tuning. As such, it is thought, that the fine-tuned model should be able to provide better embeddings as features into the SVM as it was fine-tuned for the same classification task. 

\subsection{Optimum Embedding Pooling Methodology}
\label{optimum_pooling}
As mentioned in \ref{embedding}, the type of pooling used in a model based on the transformer architecture is an important decision to be made. Typically, models based on BERT use a special \emph{CLS} (classification) token at the start of the input and use the final embedding of that single token to represent the embedding of the entire sequence. \\

\noindent
While CLS-pooling is a common technique, there is evidence in the literature that suggests alternative pooling techniques, such as mean-pooling and max-pooling, may be more suitable for in certain applications. For instance, experiments conducted for \emph{DefSent} \cite{tsukagoshi2021defsent} --- an NLP model which aimed to produce sentence embeddings for definitions of words to be similar to the word itself --- found inconclusive results on which pooling strategy worked best.\\

\noindent
For instance, when running the experiment on RoBERTa-base (recalling that CodeBERT and UnixCoder use an architecture identical to RoBERTa), they found no significant difference in the performance of the three pooling types, i.e., CLS, mean, and max pooling. SentenceBERT, another fine-tuned model trained on the same task as DefBERT, saw better performance using mean-pooling \cite{reimers2019sentence}. Finally, a paper by Ma et al., also regarding sentence embeddings of natural-language, says that despite CLS-pooling typically being used for fine-tuning for classification tasks, they found that mean-pooling performed best in all the categories they tested for \cite{ma2019universal}. This contradicts the default implementation of the sequence classification task for Roberta in HuggingFace, which uses CLS-pooling.\\

\noindent
With all this evidence in mind, it suggests we should try these three popular pooling types for our model to determine which is the best-performing for our use-case, as the literature is suggesting there is no definitively best pooling strategy. \\

\noindent
As eluded to earlier, this poses an issue as HuggingFace's default implementation of SequenceClassification for Roberta uses CLS-pooling, which means we will need to reimplement this class ourselves. Thankfully, the downstream tasks done by the CodeBERT authors show an example of how to do mean and max pooling respectively.
