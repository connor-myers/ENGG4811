\section{Similar Tasks}
There are numerous similar tasks in the literature. That is, applying machine learning to the classification of security-sensitive methods. Here we will detail the more relevant papers in the literature.

\subsection{SuSi}

\noindent
SuSi \cite{susi} is a machine learning approach for identifying sources and sinks in \emph{Android} code. SuSi uses a Support Vector Machine (SVM) classifier with 144 manually defined binary features (i.e., does the method have this feature --- true or false?) to perform its classification. \\

\noindent
For example, one of the features used is whether or not the class name the method belongs to contains the keyword `get'. While this may seem like a simple feature, which it is, when combined with 143 additional features, high accuracy can be reached.\\

% (the reason for this being that methods that are `getting' a value are more likely to be a \emph{source}; e.g., HttpServletRequest.getParameter()). 

\noindent
Importantly, this methodology is different from our proposed approach. For instance, SuSi uses manually curated features, whereas, in our approach, these features would automatically be generated. SuSi also differs from our proposed approach as it only operates on the code; no features of the Javadoc are included in the SVM. Furthermore, SuSi only classifies methods as sources, sinks, or none. It does not classify sanitisers, whereas our proposed approach does.\\

\noindent
SuSi's labelled dataset is available and open-source. However, despite the code technically being Java, we will restrict our training dataset to \emph{native} Java examples. Android Java code uses Android-only libraries and generally looks very different from `normal' Java. As such, it was thought included Android examples in the training data would negatively affect the model's performance on traditional Java code. Additionally, the dataset is not in a suitable format (it does not include Javadoc) and, if used, would require additional configuration to be useful for our purposes. \\

\noindent
SuSi performs exceptionally well, achieving an F1-score of 91.9\%.

\subsection{Swan}

SWAN is a semi-automated classifier of security-sensitive Java methods using machine learning techniques \cite{swanassist}. SWAN works almost identically to SuSi (i.e., SVM on a number of manually identified binary features), except it is trained on general Java programs and is trained on more features (206 for SWAN versus 144 for SuSi). SWAN classifies code as source, sink, sanitiser, authentication-method, or none --- which is a superset of the labels we are using. SWAN can also further classify some of these methods according to their specific CWE (Common Weakness Enumeration). However, this aspect of SWAN is not relevant to this thesis. \\

% \noindent
% SWAN employs a Support Vector Machine (SVM) approach on 206 manually defined binary features (i.e., does the method have this feature --- true or false?) to perform its classification. That is, the authors have gone through a dataset of examples of security-sensitive-methods and manually identified what aspects of a code is important for classifying it as a security sensitive method. This is decidedly different from our proposed implementation of fine-tuning a pre-trained bimodal Transformer model. \\

%\noindent
%For example, one of the 206 features SWAN classifies on is whether or not the class name the method belongs to contains the keyword `SQL' (the reason for this being that methods interacting with an SQL database are more likely to be a \emph{sink}). While this may seem like a simple feature, which it is, when combined with 205 additional features a high accuracy can be reached on a relatively small training dataset.\\

% \noindent
% The \emph{SWAN} project also includes SWAN-assist, which is an Intellij plugin that allows users to classify security-relevant methods while working on a project. SWAN includes this additional information to improve the machine-learning classifier for a particular project. Of course, this aspect is not relevant to our project, but it does inflate the model's accuracy compared to a fully-automated process such as ours. \\

\noindent
SWAN's training dataset is publicly available, and open-source \cite{swan_github}. Labelled datasets of security-sensitive methods are hard to come by, and thankfully Swan has quite an extensive list. For this thesis, we will include a subset of this dataset for our training and evaluation purposes.  \\

\noindent
This dataset does not provide the code and Javadoc associated with each method, so additional data processing is required. We will return to this topic in Chapter \ref{dataset-creation}. \\

\noindent
SWAN achieves an accuracy of $0.826$ on the classification of security-sensitive methods \cite{swanassist}.

\subsection{Sas et al.}

\noindent
Sas et al. \cite{autodetection}, like SuSi and SWAN, uses an SVM classifier on many manually curated features to perform its classification. Sas et al. uses fewer features (roughly 100) than SuSi and SWAN. Like SWAN, it is trained on general Java code. The model was trained on over 1000 methods manually identified from popular Java libraries, including Apache Commons IO\footnote{\url{https://commons.apache.org/proper/commons-io/}} and Apache HTTP Client\footnote{\url{https://hc.apache.org/httpcomponents-client-5.1.x/}}. \\

\noindent
Furthermore, Sas et al. does not classify on the same labels as SuSi or SWAN. It classifies on the four following labels: source, sink, mixed (both source and sink), and none (neither a source nor a sink). Unlike our approach, it does not include sanitisers. \\

\noindent
The SVM model achieved an average (of all classes) recall of 85\% and an average precision of 77.9\%.\\ 

\noindent
Unfortunately, the training dataset is not publicly available, so we cannot include it in our training data for this thesis.

\section{Model Architecture}
\label{model_architecture}
\subsection{CodeBERT}
CodeBERT \cite{CodeBERT} is a large pre-trained model made by Microsoft for code and natural language processing tasks. It uses an architecture identical to RoBERTa\footnote{More specifically, RoBERTa-base with 125M parameters}, and has been trained on millions of bimodal\footnote{It has also been trained on some unimodal examples for the Replaced Token Detection pre-training objective.} examples of code (Go, Java, Javascript, PHP, Python, and Ruby) and the corresponding natural language (English). This makes it suitable for downstream tasks involving the relationship between natural language and code. \\

\noindent
Since CodeBERT is based on RoBERTa, it uses the transformer architecture described in Section \ref{transformers}. CodeBERT has a maximum input size of 512 tokens (with either 509 or 510 tokens being usable, depending on what pooling strategy is used) and generates an embedding of size 768 for each provided token. \\

% As mentioned in section \ref{embedding}, we require a \emph{sequence} embedding, not a token embedding. Hence, these 512 token embeddings need to be \emph{pooled} into a sequence embedding. We can either: take the mean of all the token embeddings element-wise (mean-pooling), take the maximum value of each of the token embeddings to construct a new size $768$ embedding (max-pooling), or simply take the embedding of the first token (the [CLS] (classification) token) and treat it as a our sequence embedding. \\

% \noindent
% Because CodeBERT is trained to understand the semantic connection between code and natural language, it is suitable for tasks involving the intersection of code and natural language. CodeBERT was benchmarked on various downstream tasks, including documentation generation and natural-language code-search. While none of these tasks are a classification task, as our task is, CodeBERT can easily be augmented to be a classification model by adding an additional classification head on top of CodeBERT. \\

\noindent
Since CodeBERT's architecture is \emph{identical} to RoBERTa-base\footnote{CodeBERT and RoBERTa share an identical structure. They differ only in the values of the weights and biases of all the neurons.} we can use existing classification code for RoBERTa, a very popular and well-supported model, provided in the HuggingFace Transformer's library to implement our model.\\

\noindent
Of course, CodeBERT has not been trained on our exact task. The pre-trained model of CodeBERT has been trained two tasks that are far more general than any downstream task. Specifically, CodeBERT has been pre-trained on Masked Language Modelling (MLM), and Replaced Token Detection (RTD).\\

\noindent
In Masked Language Modelling, for each bimodal training example, 15\% of the tokens are hidden from CodeBERT, and CodeBERT must `guess' what the hidden tokens are. From this guess, and the real value of the token, a loss value is calculated. The weights and biases are then optimised from this loss using the Adam optimisation algorithm \cite{CodeBERT}. For Replaced Token Detection, CodeBERT is provided unimodal data (i.e., code \emph{or} natural language), and some tokens are replaced with arbitrary tokens. CodeBERT must then classify each token in the input as `replaced' or `not replaced'. Of course, a loss value is calculated from the model's answers, and the model is optimised accordingly. \\

\noindent
Since CodeBERT has only been trained on these two general tasks, it will need to be fine-tuned to classify security-sensitive methods accurately, as described in Section \ref{fine-tuning}.

\subsection{UniXcoder}
\noindent
UniXcoder is another large pre-trained model created by Microsoft for code and natural language understanding tasks\cite{unixcoder}. UniXcoder is similar to codeBERT in that they were both trained on the same dataset, and both models are the same size. However, these two models differ in several key areas. Most importantly is that, unlike codeBERT, UniXcoder is not trained on code directly, but rather on a special abstract syntax tree (AST) generated from the code\footnote{The pseudo-code for the algorithm used to generate the special AST can be found at \cite[pg.~3]{unixcoder}}. \\

\noindent
UniXcoder, like CodeBERT, was also trained on the MLM and RTD training objectives\footnote{UniXcoder uses additional training objectives, but these are for the decoder portion of the model, which we will not be using.}. In the CodeBERT paper, the authors hypothesised that their model was performing worse than another model, Code2Seq \cite{code2seq}, for specific tasks because Code2Seq learns the syntactic structure of programs during pre-training \cite{CodeBERT}. As such, the development of UniXcoder is an extension to CodeBERT in which the syntactic structure of the program is incorporated into pre-training. This was accomplished by training on the AST of code rather than the code directly.

\subsection{SVM tf-idf}

\noindent
Tf-idf, as described in Section \ref{tf-idf}, is a common technique to generate features for an SVM classifier \cite{sentiment-analysis-cb} \cite{sentiment-analysis-fin}. For this architecture, TF-IDF is used to generate the features (i.e., the TF-IDF value for each unique token in a text) for each input, and an SVM is trained to classify based on these TF-IDF features. 

\noindent
Because this is a simplistic and perhaps naive approach to our task, this model will be considered the `baseline model'. That is, the performance of this SVM with tf-idf represents the bare minimum performance our more advanced models should reach. \\

\noindent
SVM with tf-idf models are commonly implemented using the Python library `Scikit-learn' \cite{scikit-learn}. We will be using this library to implement this model. 

% \noindent
% Tf-idf is particularly useful for SVMs as it extracts the terms that are important for a particular label, but are not as important in other labels. Then, the features that our SVM will be trained on are simply the binary result of whether or not the provided example contains any of these important keywords or not.\\

% \noindent
% SVM with tf-idf to generate features is a common technique for natural-language classification with extensive examples of this techniques use in the literature, e.g: \cite{sentiment-analysis-cb} \cite{sentiment-analysis-fin}. \\

\subsection{SVM-Transformer Hybrid}

\noindent
A less common technique is to use an SVM (for classification) in conjunction with a Transformer encoder (for feature generation). The Transformer generates a sentence embedding, and the SVM classifies based on that embedding. This technique does have a precedent in the literature \cite{svm-with-transformer} \cite{svm-with-embeddings}. We will implement this model using Scikit-learn for the SVM classifier and both CodeBERT and UniXcoder as the encoders. \\

\noindent
This raises an interesting idea. When creating this model, there are two choices. We can either use the pre-trained versions of CodeBERT and UniXcoder, or the fine-tuned versions generated from our traditional CodeBERT and UniXcoder models (i.e., utilising a neural network classifier). \\

\noindent
Piskorski et al. carried out an experiment comparing these two approaches. As part of their evaluation of many different models, they compared an SVM model with features generated from a fine-tuned BERT model and the pre-trained BERT model. They found the SVM model using fine-tuned embeddings outperformed the SVM model using the base pre-trained embeddings by, on average, $8\%$ \cite{svm-with-embeddings}. \\

% \noindent
% To clarify how this will work: when we fine-tune CodeBERT and UniXcoder, we will add a neural network classification head on top. Then, we will fine-tune the model on the labelled data we provide it. However, since we are not freezing any of the lower-layers, the original base model (the pre-trained model) that we added the classification head to \emph{also} has its weights and biases adjusted during fine-tuning. As such, it is thought, that the fine-tuned model should be able to provide better embeddings as features into the SVM as it was fine-tuned for the same classification task. 

\noindent
We will also conduct this experiment. For our SVM-hybrid model configuration, we will run the test experiments on both the fine-tuned and pre-trained versions of the encoders.

\subsection{Optimum Embedding Pooling Methodology}
\label{optimum_pooling}
As mentioned in Section \ref{embedding}, we need to select a pooling strategy to generate a sequence embedding. Typically, models based on BERT use CLS-pooling. \\

\noindent
While CLS-pooling is a common technique, mean pooling has outperformed CLS-pooling in some circumstances. Experiments conducted for \emph{DefSent}, a natural language processing model, saw CLS and mean pooling perform similarly \cite{tsukagoshi2021defsent}. SentenceBERT, another NLP model, saw better performance using mean-pooling compared to CLS-pooling\cite{reimers2019sentence}. A paper by Ma et al., found that mean-pooling outperformed CLS-pooling on all experiments \cite{ma2019universal}. \\

\noindent
It is clear there is no best pooling strategy for all use cases. As such, we will perform all experiments involving CodeBERT or UniXcoder using both mean and CLS-pooling to compare the relative effectiveness of each pooling strategy. By default, HuggingFace's implementation of RoBERTa (for classification tasks) uses CLS-pooling. As such, we will need to run a modified version of HuggingFace's source code to implement mean-pooling. \\
