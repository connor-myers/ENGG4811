\section{Dataset Sources}

\noindent
For our machine learning model to accurately label security-sensitive methods, it will need to be fine-tuned on many labelled examples. The training dataset is arguably the most important aspect of this project. It is imperative to this project's success to create a sufficiently-large high-quality dataset of labelled security-sensitive methods. \\

\noindent
Each example in our dataset should include a Java method's code and Javadoc, as well as its security label (one of source, sink, sanitiser, or none). Unfortunately, no such database exists. This is not surprising as similar tasks extract features from byte code rather than source code or Javadoc. \\

\noindent
There are existing datasets that provide a list of security-sensitive methods, but only provide the fully-qualified method name and the example's security label. To incorporate these examples into our dataset, the source code for each method will need to be manually located, and the relevant Javadoc and code extracted from it. \\

\noindent
Datasets we can use include:
\begin{itemize}
    \item SWAN's training dataset \cite{swan_github}
    \item Default taint-analysis configurations
    \begin{itemize}
        \item SinkTank \cite{sinktank}
        \item Facebook's Infer \cite{infer}
        \item SonarQube \cite{sonarqube}
        \item SpotBugs \cite{spotbugs}
    \end{itemize}

    \item OWASP's security-sensitive method-list \cite{owasp_srm}

\end{itemize}

\noindent
Since these existing datasets do not include the method's code and Javadoc, these needed to be located ourselves. To achieve this, an intermediary dataset was created. This dataset includes the name of the method, the security-label of the method, and a link to the file (on GitHub) in which the method is located. From this information, a tool was written to dynamically scrape the code and Javadoc for each method from GitHub. This topic is explored further in Section \ref{intermediary}. \\

\noindent
Another issue is that these existing datasets lack security-\emph{insensitive} methods; they only list security-sensitive methods. This is a significant problem as it is likely that the vast majority of methods our model will encounter in a real-world context are benign and security-irrelevant. Unfortunately, there is no easy solution to this problem. To ensure the dataset includes security-insensitive methods, a number of methods were randomly sampled from various popular Java projects on GitHub and manually labelled.

\subsection{CodeCrawler}

\noindent
To dynamically build the dataset from the intermediary dataset, \emph{CodeCrawler} was developed. CodeCrawler is publicly available on GitHub\footnote{\url{https://github.com/connor-myers/CodeCrawler}}.\\ 

\noindent
CodeCrawler scrapes the code and Javadoc for a particular method from GitHub. Furthermore, CodeCrawler does some basic pre-processing on the data. For the code, in-line comments and new-line characters are removed. Additionally, HTML code, URLs, and new-line characters are removed from the Javadoc. 

\section{Dataset Manager Tool}

\noindent
The Dataset Manager Tool\footnote{\url{https://github.com/uqcyber/SecurityMethodClassifier/tree/main/tools/dataset-manager}}, as its name suggests, manages the intermediary dataset format. This tool provides a variety of useful functions for manipulating the dataset. Below is a brief summary of this program's functionality.

\begin{itemize}
    \item \textbf{Remove Duplicate:} Removes duplicate entries in the dataset. Duplicate here meaning methods mentioned multiple times, as well as files. If a file is listed multiple times, the methods contained in duplicated files are combined under one file entry.
    \item \textbf{Merge:} Merges two or more intermediary datasets together. Implicitly removes duplicates.
    \item \textbf{Licensing:} For all files with unknown licenses in the dataset, the tool uses \emph{ScanCode} to automatically detect the license of the file and updates the dataset accordingly.
    \item \textbf{Statistics:} Provides statistics for the dataset.
    \item \textbf{Generate:} Uses CodeCrawler to parse code and Javadoc for each method; constructs training and validation datasets from this.
\end{itemize}

\subsection{Limitations of the Dataset}
\label{dataset_limitations}

\noindent
There are some key limitations to the training and validation datasets that are worth discussing. The most significant limitation is how the datasets are split. Because a small number of projects were used in the dataset, it was not practical to isolate the examples from a particular project to just one of the training or validation datasets. Rather than isolating examples based on the project they came from, examples were instead isolated based on the file they are in. That is, a file with multiple methods associated with it must contribute \emph{all} its methods to just one of the training or validation datasets. This was done to reduce the bias in the validation dataset. \\

\noindent
Another limitation is that the proportion of labels in the validation dataset likely does not reflect a real-world use case. For instance, it is likely that in a realistic scenario the majority of methods are security-insensitive. That is, they are neither sources, sinks, nor sanitisers. This is not the case for the validation dataset, which likely has an inflated proportion of security-sensitive methods compared to a real-world Java project.\\

\noindent
For these reasons, the model's performance on the validation dataset will likely be inflated. Therefore, the validation dataset is better used to configure model hyperparameters rather than as a metric for the model's real-world performance.

\section{Test Dataset}
Due to the limitations discussed in Section \ref{dataset_limitations}, to get an accurate figure for the performance of the trained model, a test dataset should be created. \\

\noindent
This test dataset should reflect the proposed real-world use case of our model. Recall that our model aims to accurately label security-sensitive methods to configure taint-analysis tools for Java projects. As such, our test dataset should reflect this use case. \\

\noindent
For our test dataset, we randomly sample 165 methods (same size as the validation dataset) from Apache's Log4J\footnote{\url{https://logging.apache.org/log4j/2.x/}}, and manually label these methods. Comparing the model's predictions to our manually-generated labels will provide a measure of our model's performance in a real-world setting. \\

\noindent
Log4J was chosen because it is a popular and open-source Java library with catastrophic security exploits in the past \cite{log4shell}. \\
