\section{Dataset Sources}

\noindent
For our machine-learning model to accurately label security-sensitive methods, it will need to be trained on many labelled examples. Arguably the dataset is the most important aspect of this project. It is imperative to this project's success that we create a sufficiently-large high-quality dataset of labelled security-sensitive methods. \\

\noindent
Recall that for our model, our labelled examples need to be in the following form: A Java method's code and documentation, and a label (one of: source, sink, sanitiser or security-irrelevant). Unfortunately, no such database exists in that form. However, this is not surprising as tasks of a similar nature typically extract features from byte-code (i.e., no natural-langauge processing directly on the source-code), and choose to neglect documentation as well. However, these similar datasets are not completely useless. In-fact, they provide a good starting point for us to create our dataset. While they do not have the code and the documentation included, they do provide high-quality labels. It is cumbersome and time-consuming, but manually locating the source-code for these numerous examples is worth-while given the quality of these examples. \\

\noindent
These similar datasets include:
\begin{itemize}
    \item SWAN's training dataset \cite{swan_github}
    \item Default taint-analysis configurations
    \begin{itemize}
        \item SinkTank \cite{sinktank}
        \item Facebook's Infer \cite{infer}
        \item SonarQube \cite{sonarqube}
        \item SpotBugs \cite{spotbugs}
    \end{itemize}

    \item OWASP's security-sensitive method-list \cite{owasp_srm}

\end{itemize}

\noindent
All the above datasets provide high-quality labelled examples of security-sensitive methods. Unfortunately, they are unsuitable for a variety of reasons and will require some augmentation to be of any use to this project. Namely, as has already been mentioned, they only provide a fully-qualified-name of the method and a security-sensitive label. They do not provide the code and the Javadoc which is essential to our approach. Furthermore, their security-sensitive labels are typically a subset of the labels we will be using. For instance, SinkTank only has labels for sources and sinks. This means there will be substantially fewer \emph{sanitiser} examples in the dataset; ideally we would like all our security-sensitive methods to occupy a similar proportion of the dataset. More concerningly, however, is that none of these existing datasets have labelled security-\emph{insensitive} methods. This is a signficant problem as it is likely the vast majority of methods our model will see in a real-world context are benign security-irrelevant methods. Accurately labelling security-irrelevant methods is imperative for this project as configuring taint-analysis tools with false-positive security-sensitive methods will in-turn lead to additional benign dataflows being considered malicious by the taint-analysis tool. \\

\noindent
For the first issue, that these existing databases do not include the code and the documentation, there is unfortunately no simple solution. For each example, the source-code needs to be manually located, with the code and the documentation for the relevant method's extracted accordingly. This can be semi-automated as there is a finite number of projects and the fully-qualified-name provides information on where to locate the method \emph{within} a project. That is, we download all the projects that all the examples come from and write a script to locate the method's source-code within that project, using the fully-qualified-name to locate it. Our approach we took was similar to this, but complicated by the fact we wanted the dataset to be generated dynamically. That is, for each example, it will download the code from Github and extract the code and documentation automatically. We will return to this topic later. \\

\noindent
For the second issue, of having an inadequate number of sanitiser examples and have \emph{no} security-insensitive examples, again, there is no easy solution for this. All security-insensitive labels were done by me. Popular open-source Java projects were obtained (Google Guava, ElasticSearch, Apache Commons, etc...) and a random sample of methods were extracted. I then manually labelled these examples. Naturally, as they were random samples from real-world Java projects, the majority of the examples were security-insensitve. Of course, manually labelling these examples is not ideal. I am not a security-expert and undoubtedly this lowered the quality of the dataset. We will return to this point in the limitations section of this thesis. \\

\section{Intermediary Dataset Format}

\noindent
For our approach, it would be unwise and na\"ive to have our dataset simply be a large json file with a number of code, documentation, label tuples. At this stage of the project, we only require code and documentation --- but what about the future? With these machine-learning models, we can provide all sorts of information as training-data. Given that the dataset is arguably the most important deliverable of this thesis project, it would make more sense for the dataset provided to be applicable to other projects. Furthermore, the dataset should be made in a such a way that it is easily extensible. \\

\noindent
For example, if for this thesis we simply provided a list of examples (code, documentation, label) we would not be able to easily extend our dataset. One extension task we may want to perform in future is to include AST information of a method into the training data. In that case, we would need to manually locate these files all over again, download them, pre-process them, etc., and create our training set from that. For these reasons, it would be much more appropriate to create an intermediary dataset that includes information needed to dynamically build the dataset (i.e., a link to the source-code) and create a tool to automatically download the source-code for these examples, parse the code, extract the relevant data, etc., and dynamically create our training dataset. \\

\noindent
Figure \ref{intermediary_dataset} shows the format of our intermediary dataset for one file. It uses the yaml file format and includes all the information we need to build the dataset using an additional tool. Namely, it includes a link to the file on GitHub that the method is located in, as well as the name of the method and its label. We do not differentiate between overloaded methods (i.e., same name, different arguments) as we assume they all the same security-label. Furthermore, we only create one entry for each file (rather than each method) so we do not fill the dataset with redundant information. We organise the dataset around files instead of projects because we download each file of a project individually, rather than the entire project. License information for the file is also included as some licenses are incompatible with each other. License information for each file was extracted automatically using an OSS tool called \emph{ScanCode}\footnote{\url{https://github.com/nexB/scancode-toolkit}}. It is worth nothing that two different files in the same project can have different licenses. Furthermore, we also include the root class type for each file (i.e. class, abstract class, interface). Additionally,  although it is within the Java specification to have multiple root-classes for a single file, this is never done so we ignore that case.

\subsection{CodeCrawler}

\noindent
To dynamically extract code and documentation (as well as pre-process the extracted data), I wrote a Python tool called \emph{CodeCrawler}. CodeCrawler is publicly available on GitHub\footnote{\url{https://github.com/connor-myers/CodeCrawler}}.\\ 

\noindent
CodeCrawler scrapes the code and Javadoc for a particular method, given the method's name and the location of the file on GitHub. Furthermore, CodeCrawler does some basic pre-processing on the data. For the code, in-line comments and new-line characters are removed. For the Javadoc, HTML code is removed, as well as links, and new-line characters. 

\section{Dataset Manager Tool}

\noindent
The Dataset Manager Tool\footnote{\url{https://github.com/uqcyber/SecurityMethodClassifier/tree/main/tools/dataset-manager}}, as its name suggests, manages the intermediary dataset format. This tool provides a variety of useful functions for manipulating the dataset. Below is a brief summary of this program's functionality.

\begin{itemize}
    \item \textbf{Remove Duplicate:} Removes duplicate entries in the dataset. Duplicate here meaning methods mentioned multiple times, as well as files. If a file is listed multiple times, the methods for all the files (that duplicated) are combined to be under one file entry.
    \item \textbf{Merge:} Merges two datasets together. Implicitly removes duplicates.
    \item \textbf{Licensing:} For all files with unknown licenses in the dataset, uses \emph{ScanCode} to automatically detect the license and update the dataset.
    \item \textbf{Statistics:} Provides statistics for the dataset.
    \item \textbf{Generate:} Uses CodeCrawler to parse code and Javadoc for each method; constructs training and validation datasets from this.
\end{itemize}
